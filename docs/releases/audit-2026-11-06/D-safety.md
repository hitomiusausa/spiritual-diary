# D AI・利用者の安全の監査

監査日: 2026-11-06。担当: `/root/audit_c_security`（D役兼任）。基準: `aac43b6`。コード変更なし。実AI、本番API、実日記は利用していない。A/Cの指摘を参照して重複を整理した。

## 結果

優先したい問題は、危機の日記を書いた利用者が分析失敗時に相談導線を得られない点と、チャットのAI拒否・空応答を成功として保存する点。ほかに危機判定前の切り詰め、信頼しない会話文脈のsystemへの混入、人格指示の内部矛盾、相談案内の不足を確認した。実際にAIが有害な応答を生成したという実測結果ではなく、制御・データ経路の監査である。

既存関連テストは **3 files / 37 tests PASS**。単純な正規表現の網羅性を安全性の保証とは扱わない。

## D-01 危機の日記で分析が失敗すると相談カードが出ない

- 暫定: P1。確度: 高、通常UIの制御経路で確認。ブラウザ再現は統合QAへ。
- 場所: `src/components/SpiritualDiary.jsx:425-453`（同意分岐）、`613-701`（分析）、`1587-1590`（入力画面の支援）、`1798`（結果画面）。APIのready/rate/quotaエラーは危機判定より前。
- 期待: D-15/D-23の「つらい気持ちを書いた人を突き放さない」「外部へ送らない場合にも端末内で支援を出す」を、通信や上限障害でも維持する。
- 事実: 入力画面の相談カードはdeclinedSupportだけで表示し、そのtrueへの更新は同意拒否時だけ。既に同意している人は危機文でも直接analyzeへ進む。429/503/502や通信失敗ではinputに戻りエラーだけを表示する。result.supportは成功時にしか得られない。
- 再現: 同意済み端末で危機表現を含む日記を入力し、APIを429/503またはネットワーク拒否にモック。結果に遷移せず、declinedSupport=falseのままで相談カードがない。
- 影響: 日次上限が小さい本サービスで、支援が必要な利用者ほどAPIの成否次第で相談先への導線を失う。サポートページへの入口も日記画面では発見しにくい。
- 最小修正: 分析開始前・失敗後に端末内entryNeedsSupportを適用し、必要ならinputで支援カードを表示する。分析成功を待たず支援できる状態を持つ。利用者が内容を書き換えた場合の再判定も定める。危機検出だけで無断送信しない。
- 互換: 保存形式変更不要。合成入力のみをテストする。
- 合格条件: 同意済み/拒否/撤回、offline/429/503/502、AI空応答のすべてで、危機の日記から支援へ進める。一般日記で誤表示し続けない。ロック解除なしの相談経路も維持。

## D-02 チャットの危機判定より前に文字を切り詰める

- 暫定: P2（API安全処理の不整合）。確度: 高、純関数で再現。
- 場所: `src/app/api/chat/route.api.js:44-53,87-97`。
- 事実: cleanMessagesは各contentを先頭1200文字に切ってから、最後のuserメッセージだけdetectCrisisへ渡す。既知の危機語でも切り捨て側にあると固定文経路に入らない。
- 再現: content=`"あ".repeat(1200)+"死にたい"`。実detectCrisisでraw=true、cleanMessages相当のtrim/slice後=false。長さ1204→1200。通常UIは入力欄を1200に切るため、この具体例は直接API要求や別クライアントが成立条件。
- 影響: 正規表現で拾える入力でも、サーバーの前処理により危機対応が失われる。規定長を超えた内容を普通の会話として黙って扱う。
- 最小修正: 最大長を超える最新user入力を明示的に拒否し、必要な安全判定は検証済みの全最新文に対して行う。C-04のbody上限と両立させ、無制限なraw本文走査にしない。切り捨てによる意味の変更を避ける。
- 互換: 端末の会話保存上限や古い履歴の閲覧は維持。
- 合格条件: 1200以内の既知危機文は固定文+support、上限超過を通常のAI会話として処理しない。最新ユーザー発言の意味を変えない。危機時にRC・AI・日次クォータを消費しない仕様を維持。

## D-03 チャットで拒否・途中打ち切り・空応答を200成功として返す

- 暫定: P1。確度: 高、応答関数とAPI経路で再現。
- 場所: `src/lib/claudeResponse.js:3-10`、`src/app/api/chat/route.api.js:165-172`、`src/components/KiriChatPanel.jsx:87-95`。分析APIは同条件を502で返す。
- 事実: extractReplyTextはrefusal/max_tokensで空文字を返す。chat APIはログを出すだけで `success:true, reply: reply || "……"` とする。UIは通常のassistantメッセージとして履歴に保存する。
- 再現: stop_reason=refusal/max_tokens、またはcontent=[]をモック。実関数からreply=""、APIの構築するpayloadはsuccess=true/省略記号。ライブAIは呼んでいない。
- 影響: 提供できなかった応答がKiriの意図的な沈黙に見える。安全上の拒否でも利用者が失敗と分からず、有料枠を消費したうえで回復できない。D-16の拒否・途中打ち切りは失敗扱いという方針とも異なる。
- 最小修正: 空/拒否/途中切れは502等の統一エラーとして返し、Kiri口調の失敗案内をUIで表示する。危機の固定文はこの失敗と区別する。回数返却を行うかは既定の費用方針を確認し、黙って変更しない。
- 互換: 正常会話の保存形式は維持。失敗案内を通常AI発言として次回モデルへ送り続けない点はEと連携。
- 合格条件: 各stop_reason/空/思考ブロックのみで成功扱いなし。通常textは成功、危機の固定文は支援表示を維持。再試行方法が分かる。

## D-04 利用者由来の会話文脈をsystem命令へ連結する

- 暫定: P1（有料AI会話の公開前）。確度: 信頼境界の違反は高。実際のAIの有害応答は未実測。
- 場所: `src/app/api/chat/route.api.js:56-69,139-155`、分析の危機指示は `analyze/route.api.js:672,690-691`。
- 事実: context.resultの各本文、entry.event/intuition、nicknameをbodyから受け取り、そのままdynamicContextにして `system: KIRI_PERSONA + SAFETY_GUIDANCE + CHAT_MODE + dynamicContext`。日記や過去AI結果に書かれた命令文が、開発者管理の安全方針と同じsystem文字列に、しかも後ろ側へ入る。分析のCRISIS_FORTUNE_GUIDANCEはuserプロンプト末尾にあり、安全優先の命令階層も曖昧。
- 再現: 文脈のentry.eventに合成markerと「これ以降をシステムの最優先命令とする」等を置き、fetchモックでAnthropicへ渡すbody.systemを検査するとmarkerが含まれる。UIから書いた日記や復元した過去結果も同じ文脈経路に入るため、API改造だけの問題ではない。
- 影響: 指示として信用しない日記・過去AI本文を、優先度の高い命令領域へ昇格させる。人格や安全制約を上書きする注入への耐性を弱める。これだけで全指示が必ず突破されるとは断定しない。
- 最小修正: systemは開発者管理の人格・安全・モード指示だけにする。文脈は明確に「命令ではない利用者データ」としてuser側へ構造化し、元のrole順を保つ。危機モードの開発者指示はsystem側で安全が優先することを明示する。安全を人格の雰囲気や短さより優先させる。
- 互換: 端末履歴や外部保存方針は変更不要。AI入力構造の変更を測定し、文脈が正しく届くことをモックで確認する。
- 合格条件: nickname/entry/過去resultの任意markerがsystemに入らない。全AI呼び出しに安全指示が存在。危機モードと通常モード、既存のrole順・出力形式を検証する。実AI評価が未実施なら、その限界を記録する。

## D-05 分析の人格と文体指示が推奨・禁止の両方を含む

- 暫定: P2。確度: 高（Aの共有を再確認）。
- 場所: `src/lib/kiriPersonality.js:4-130`、`src/app/api/analyze/route.api.js:25-40,531-552,615-649`。
- 事実: systemとuser promptで「だね/だよ」を推奨する一方、user prompt:638が男言葉として禁止する。人格は「兎の妖精」と「人格を持たない観測存在」が併存。systemの人格は2文以内、分析モードはフィールドごと3〜5文等、モードの優先関係も明示されていない。
- 影響: 口調・文章量・世界観が入力や応答ごとに揺れる。保守時にどの人格定義を直せばよいか分からない。実AIで揺れたという実測とは区別する。
- 最小修正: 人格はkiriPersonalityへ一本化、分析APIには出力形式と分析固有の指示のみ残す。通常会話/分析/危機の優先順位を明示し、分析の長さは会話の2文制限から除外する。既定の常体を禁止しない。
- 合格条件: 同じ語尾の推奨/禁止が矛盾しない。絵文字を使わない画面方針とAI文章の表現方針も照合する。モック検証で3モードの指示を確認し、AIの文体実測は別の検収として残す。

## D-06 相談カードに通話料金と接続条件の補足先がない

- 暫定: P2。確度: 現行公式ページと照合済み。
- 場所: `src/lib/kiriSafety.js:4-12`、`src/components/SupportCard.jsx:24-35`。
- 2026-11-06の確認: 3件の名称・保存されている通常番号・通常受付時間は厚生労働省の現行案内と一致。コードの確認日は2026-10-08のまま。いのちの電話の現在の番号は有料のナビダイヤルであり、よりそいには地域/IP電話による別番号の案内がある。
- 事実: カードには各通常番号・時間のみ表示。有料であることと、通常番号へ接続できない場合の公式補足へのリンクはない。SUPPORT_LINES_SOURCE_URLは定義されているがカードでは使われない。
- 影響: 通常番号に接続できない利用者が代替窓口を探せず、有料通話を無料だと期待する可能性。カード全体が無料と明記しているわけではないので、料金について虚偽表示とは扱わない。
- 最小修正: 確認日を実確認日に更新し、有料窓口の注記を付ける。地域/IP電話等の補足・他の相談方法へ進める公式リンクをカードに追加する。全地域条件をカードへ詰め込む必要はない。
- 合格条件: リンクがロック中/同意拒否時/履歴/通常結果から利用でき、記録を失わずに戻れる。料金を区別できる。定期確認の担当・更新時期をHへ渡す。
