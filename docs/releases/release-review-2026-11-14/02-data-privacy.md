## R2-01 [P1] 入力画面の「すべて削除」で書きかけの日記が消える（D-40 の退行）

- 場所: `src/components/SpiritualDiary.jsx:1305-1309`（`performDelete` の `if (all) { … clearAll(); … }`）と `:1002-1006`（`clearAll` が `entry` を空にする）。入口は D-40 で入力画面に足した `:1688-1708`。
- 起きること: 入力画面で出来事を長く書く → 左上の「記録」を押す → 古い記録を見て「すべて削除」→「削除する」。記録と会話が消える。同時に、まだ読み解いていない（保存していない）入力欄の文章も空になる。確認ダイアログの文は「日記の記録・読み解き・Kiriとの会話がすべて消え」だけ。書きかけが消えることは書かれていない。
- なぜ退行か: D-40 より前は、入口が結果画面だけだった。結果画面の `entry` は読み解き済みで、履歴に保存されている。だから `clearAll()` で消えても損はなかった。今は保存前の文章が消える。
- 確かさ: 高。制御の流れはコードを読んで確かめた。ブラウザでは再現していない。
- 直し方の案: `clearAll()` を呼ぶのは `step === 'result'` のときだけにする。または `setResult(null)` だけ行い、`entry` は残す。`historyEntry.test.js` に「入力中に すべて削除 しても entry.event が残る」というテストを足す。

## R2-02 [P1・オーナー判断] 31件目で最古の日記が通知なしに消え、バックアップからも戻せない

- 場所: `src/lib/history.js:66-68`（`.slice(0, MAX_HISTORY_ITEMS)`、上限30）と `src/lib/backup.js:62-63`（空き枠が0なら取り込まない）。
- 実行で確かめた結果（合成データ）: 30件保存し、書き出して、31件目を保存 → `day0` が消えた。その書き出しを読み込むと `historyAdded:0, historySkipped:1` で、`day0` は戻らない。
- 起きること: 毎日1回読み解く人は、約1か月で最初の日記から順に消えていく。消える瞬間に画面には何も出ない。サポートの FAQ「記録が消えてしまいました」は「バックアップから復元できます」と書いている。しかし30件そろっていると戻せない。上限30件は、プライバシーポリシー2節に1行あるだけ。アプリ画面と FAQ には書かれていない。
- 位置づけ: 上限30件は D-06（暫定確定）が決めた既存の方針で、コードの不具合ではない。ただ D-40 で「日記として読み返す体験」を強めた。App Store でも「日記と内省」として出す。それなのに古い日記が黙って消える。利用者から見ると「日記が消えた」事故そのもの。公開前にオーナーの判断が要る。
- 直し方の案（どれか）:
  (a) 上限を大きくする。Preferences の1値の大きさは D-31 の会話1,000件より小さい見込み。
  (b) 29件目あたりで「古い記録から消えます。書き出しておいてね」と知らせる。
  (c) 最低限、FAQ と「最近の記録」の一覧に「新しいものから30件まで」と書く。

## R2-03 [P2] 履歴に壊れた1件があると、その後の読み解きが保存されない

- 場所: `src/lib/dataIntegrity.js:132`（1件でも検証に落ちると、キー全体を隔離する）、`src/lib/history.js:64`（`assertDataWritable` が保存を止める）、`SpiritualDiary.jsx:965-970`（「再試行するか、バックアップを書き出してください」と出す）。
- 起きること: 読み解きは表示される。しかし `saveHistory` が `DataRecoveryRequiredError` を出す。`failedKeys` は空のままなので、「保存を再試行」のボタンは出ない。押せたとしても `retryStorageWrites` はこのエラーの対象外。修復用の書き出し（`buildRecoveryBackup`）に入るのは元の生データだけで、新しい読み解きは入らない。アプリを閉じると、新しい読み解きは消える。いまアプリの中で直す方法は「すべて削除」しかない。
- 確かさ: 中。流れはコードで確かめた。壊れた記録ができる経路は、今の UI からはほぼない（文字数の上限が 100,000 字、件数の上限が30件）。まれ。
- 直し方の案: この場合の案内文を「読み込めない記録があるため、今回の読み解きは保存されていません」に変える。または有効な記録だけを使って保存を続ける。どちらにするかは B-04 の方針（原本は自動で上書きしない）と合わせて判断する。

## R2-04 [P2] 「危機を検出」というログ行がサーバーに残る

- 場所: `src/app/api/analyze/route.api.js:521`、`src/app/api/chat/route.api.js:100`。`wrangler.jsonc` で `observability.logs.enabled: true`（`invocation_logs: false`）。
- 内容: 本文・IP・ID はログに出ていない（console の呼び出しは全部確認した。C-01/C-05 の修正も維持されている）。ただ「この時刻のリクエストの日記に危機表現があった」は日記から導いた心の健康の情報で、Cloudflare Workers Logs に数日残る。D-18 には「日記由来のデータを保存しない」、ポリシー3節には「入力内容は含めません」とある。厳しく読むと食い違う。呼び出しログは切ってあるので、IP とは結びつかない見込み。ただし、Workers Logs の各行に付く `$workers` の付帯情報は実物で確かめていない。
- 直し方の案: 次のどちらか。(a) 件数だけ数える（ログ行を出さない）か、ログを消す。(b) ポリシー3節に「件数の把握のため、危機表現を検出した回数を本文なしで記録します」と書き足す。

## R2-05 [P2] プライバシーマニフェストに収集データの申告がない

- 場所: `ios/App/App/PrivacyInfo.xcprivacy`。Required Reason API の UserDefaults CA92.1 と FileTimestamp C617.1 は、実際の使い方（Preferences と Filesystem の readdir/stat）と合っている。`NSPrivacyCollectedDataTypes` と `NSPrivacyTracking` の項目はない。
- 食い違い: 申告の下書き（`docs/plans/2026-10-09/kiri-phase4-appstore-drafts.md:166`）では、日記本文を「Other User Content / Collected / App Functionality / Not linked」と申告する予定。Apple は、マニフェストの内容をアプリのプライバシーレポートに使う。マニフェストが空だと、App Store の表示とずれる。RevenueCat の分は、同社の SDK に付いているマニフェストでまかなえる見込み。
- 確かさ: 中。審査で必ず差し戻されるわけではない。
- 直し方の案: `NSPrivacyTracking=false` と、Other User Content（Linked=false・Tracking=false・Purposes=AppFunctionality）を足す。App Store Connect の回答と同じ内容にそろえる。

## R2-06 [P2・推測] RevenueCat の端末ログ

- 場所: `src/lib/purchases.js:134`。`configure({ apiKey })` だけで、`setLogLevel` を呼んでいない。SDK の型定義（`definitions.d.ts:399`）では、リリース版の既定が INFO。
- 内容: `loggingBehavior: "none"` が止めるのは Capacitor のログだけ。RevenueCat ネイティブの os_log は止まらない。INFO に匿名の App User ID が出るかどうかは確かめていない。Mac をつないだ端末のログでしか見えないので、影響は小さい。
- 直し方の案: `Purchases.setLogLevel({ level: LOG_LEVEL.WARN })`（または ERROR）を configure の前に呼ぶ。

## 問題なしとしたもの（確認した範囲）

- 保存（`storage.js`）: キーごとに書き込みを直列にしている。古い書き込みが後の操作を上書きしない。初期化に失敗しても古い localStorage へ戻らない。Web の容量超過は overlay と failures で扱っている。再試行の前の衝突チェックもある。B-01/B-05 の修正は妥当。
- すべて削除: 記録・会話・分析キャッシュ・データ不良の印・一時バックアップ（iOS）を消している。書き出し中は止める。失敗したら成功と出さない。プロフィール・同意・ロックを残すのは仕様どおりで、ポリシー5節とも合う。
- 会話: 送信中に削除やパネル閉じがあっても、古い応答を採用しない（B-03 の修正）。送るのは直近12件と、ニックネーム・記録・結果だけ。同意画面 v2 と、ポリシー3節の説明に合っている。
- 送信先: `fetch` は `/api/analyze` と `/api/chat` の2つだけ。広告や解析の SDK はない。サーバーは日記を保存しない（Redis に置くのはカウンタと HMAC 化したキーだけ）。D-18 どおり。
- ログ: サーバーとクライアントの `console.*` を全部見た。本文・IP・ID・ハッシュは出ていない。上流 API のエラーも、決まった言葉にだけ置き換えている（`providerFailure.js`）。
- ロック: ロック画面は z-90 で、ほかのモーダル（最大 z-85）より上。本体には `inert`＋`aria-hidden` が付き、起動時はロックの判定が画面の表示より先。バックアップの書き出し（修復用を含む）は再認証が必要。バックアップにはロック・同意を含めない。共有シートと復帰直後の一瞬の表示は、D-25 で受け入れたリスク。
- iOS 設定: `loggingBehavior: none`、`webContentsDebuggingEnabled: false`、`CapacitorHttp` 無効。Info.plist にある使用目的の説明は Face ID の1つだけで、使っている機能と合っている。
- 書きかけの退避（`entryDraft`）: sessionStorage に1時間だけ置き、取り出したら消す。サーバーへは送らない。
