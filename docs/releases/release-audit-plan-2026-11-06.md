## 3. 全体の順番

1. **うさこ: 対象と監査用環境を固定する。** Git差分・未追跡資料・設定ファイルの所在を確認し、Git外へ対象ファイルと差分をバックアップする。秘密の値や個人の日記本文を出力しない。配布用変更を含む基準を保存し、隔離した監査用環境を用意する。
2. **うさこ: 対象台帳を作る。** ページ、画面状態、モーダル、結果セクション、API、保存キー、外部送信先、ネイティブ連携、ビルド設定を列挙し、主担当を割り当てる。追跡ファイルの対象一覧と照合し、除外には理由を残す。
3. **領域担当: まず監査とリスト化を行う。** 同じ基準コードに対してコード読解、既存テスト確認、必要な再現を行う。監査中はアプリコードを修正しない。
4. **うさこ: 横断確認と統合を行う。** 重複と担当間の抜けを整理し、機能間の組合せを検証する。重要な指摘は別の担当が証拠を確認する。
5. **Astra: 全報告を読んで修正順を裁定する。** 実運用への影響、発生条件、回復可能性、依存関係を根拠に並べ、修正の合格条件を決める。
6. **実装担当: 裁定順に修正する。** 小さい課題単位で実装し、対象の回帰確認を行う。共有ファイルの編集は順番を決める。
7. **別担当・うさこ: 修正を検証して統合する。** 元の再現が解消し、既存データと隣接機能が保たれることを確認する。
8. **Astra・うさこ: 残件とリリース判断をまとめる。** 実機・外部接続・提出準備の未確認を明示し、引き継ぎを更新する。

## 5. 全担当共通の確認方法

各対象を以下の軸で確認する。該当しない軸も、理由を記録して未確認と区別する。

- **構造:** UI・計算・保存・通信の責務、状態の正本、非同期順序、キャンセル、イベント解除、重複実行。
- **データ:** 読む・書く・更新・削除・復元の全経路。成功表示と永続化完了の一致。上限到達時に失うものの説明。
- **セキュリティ:** 入力/保存/AI応答を信用しない検証、API権限、秘密・本文の漏えい、ネットワークと外部遷移。
- **安全:** 危機時の支援、誤解を招く断定、不適切なAI応答、エラー時にも残る相談導線。
- **導線:** 初回/再訪、次へ/戻る/閉じる、やめる、失敗後の再試行、入力維持、現在位置と状態の理解。
- **見やすさ:** 通常/大きい文字、長文/空欄、背景と文字、見出し階層、スクロール、タップ・キーボード・読み上げ。
- **世界観:** D-13/D-29/D-32〜36を基準に、明朝=見出しとKiriの声、角ゴ=操作と本文、色の役割、余白によるまとまり、穏やかな文体を確認。既存の決定を黙って覆さない。
- **運用:** 上限、費用、外部サービス障害、タイムアウト、端末再起動、アプリ更新、設定不備、診断と回復方法。

重点シナリオ:

1. 復元前に空データを書かない。保存失敗・容量不足・破損時に成功扱いしない。
2. 旧形式・同じID・不正形式・大容量のバックアップで既存記録を壊さない。途中失敗でも回復できる。
3. 分析中の戻る/連打/背景移行/日付変更/削除で、別の記録や古い結果が復活しない。
4. 同意拒否・撤回・端末復元後の送信条件が仕様どおり。支援導線は必要な状態で使える。
5. 購入の取消/保留/復元失敗/期限切れ/通信断/再インストールで、権限と表示が一致する。
6. ロック中、認証中、共有シート中の背景移行・復帰を組み合わせる。D-25で受け入れたリスクと追加の不具合を分ける。
7. 各画面の長い日本語、大きい文字、キーボード表示、重なるモーダル、エラー、空状態を確認する。
8. APIやRedis等の障害時にも、データ保護・料金制限・利用者への説明を確認する。

## 7. Astraに渡す判断基準

Astra（利用可能な `gpt-6-astra`）には全報告・対象台帳・現行の決定を渡す。重大度と作業順を分けて判断する。

| 区分 | 判断の目安 |
|---|---|
| P0 | データ消失・漏えい・誤課金・深刻な安全問題など。成立条件と影響に基づき最優先で対応 |
| P1 | 保存/復元、権限、基本導線、公開必須機能などが実用に耐えず、リリースを阻害 |
| P2 | 読みにくさ、重要な説明不足、アクセシビリティ、障害時の回復など。操作不能ならP1以上に引き上げる |
| P3 | 実害が限定的な一貫性や保守性の改善。必要性と回帰リスクで採否を決める |

順位の根拠は、被害の大きさ、起きやすさ、影響人数、回復できるか、検知できるか、公開必須条件、他の修正への依存、修正による回帰リスク。

Astraの成果には、実施順・担当・先行条件・完了条件・公開阻害か・保留理由を含める。根拠不足や担当間で見解が割れた指摘は、追加検証へ戻す。保存方式や商品条件など承認済みの方針を変える提案は、通常の不具合修正と分けて具体案をひちゃんへ示す。

## 8. 修正と検証の進め方

- 既存データに触れる修正は、Git外のバックアップ、合成した旧データ、移行/失敗時の回復方法を先に用意する。
- 1課題または密接な課題群ごとに修正し、元の再現条件と隣接機能を確認する。監査で示された実害を解消する範囲に絞る。
- 保存、認証、権限、非同期処理の修正は意味のある回帰テストを追加する。見た目だけの小さな変更は実画面で比較する。
- 同じファイルへの並行編集を避け、特に `SpiritualDiary.jsx`・`globals.css`・共有設定は編集担当を一本化する。
- 修正担当以外が差分と再現を確認する。必要ならAstraが影響の大きい修正を再レビューする。
- 共通ゲート: `npm test`、`npm run lint`、`npm run build`、`npm audit --omit=dev`。既存の失敗があれば基準時点の失敗と区別する。
- Web成果物は秘密混入・購入コード混入の検査、APIはモックで失敗と権限の境界を検証する。Cloudflare固有の挙動は隔離設定で確認する。
- ブラウザはWebKitを必須とし、375px/402px/1280pxを確認する。Chromiumも基本動作を照合する。大きい文字と読み上げは別途確認する。
- iOS変更は同期/ビルドとシミュレータで確認し、署名済み成果物のID・設定・manifestを確認する。実機必須の項目はひちゃんが順に確認できる短い手順を用意する。
- テストには合成日記と隔離した保存領域を使う。本番API・Redis・RevenueCat・実購入に依存する検証は条件と実行範囲を具体化してから行う。
